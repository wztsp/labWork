## 三、接口/数据验证要点（真实数据）

- 全站 `/api/*` 请求在浏览器测试期间**未发现任何 500 / 404**。
- 分页响应字段 `total / current / size` 原被全局 Jackson 序列化为字符串（如 `"total":"208"`），导致前端 `<el-pagination>` 的 `:total` 收到 String 而触发类型告警——已修复（见下）。
- 供应商评价接口原来返回 `onTimeRate / rejectRate` 为 0-100 的百分比，前端错误地再乘 100，显示成 `10000.0%`、`3333.0%`——已修复，现正确显示如 `100.0% / 33.3%`，自动分、综合分也正确（如 QA 供应商 综合分 97.00）。

## 四、缺陷修复（本次已修复）

### 缺陷 1：供应商评价「准时率/拒收率」超过 100%（显示 10000%）
- **现象**：/reagent/supplier-evaluate 页准时率显示 `10000.0%`、拒收率 `3333.0%`、综合分异常。
- **根因**：后端 `SupplierEvaluateServiceImpl` 已把比率算成 0-100 的百分比（`on_time/total*100`）；前端 `formatRate()` 又执行 `(v * 100)` 二次放大，导致放大 100 倍。
- **修复**：
  - [supplierEvaluate/index.vue](file:///D:/traeitem/labWork/LIS-clinical-lab-solution/lis-frontend/src/views/reagent/supplierEvaluate/index.vue#L92-L96)：`formatRate` 去掉 `* 100`。
  - 同步修正 `rejectClass` 阈值：`v > 0.2` → `v > 20`（按百分比口径），否则拒收率稍高就被标红。
- **验证**：后端接口现返回 `onTimeRate=100.0`、`rejectRate=33.33`，前端将渲染为 `100.0% / 33.3%`。

### 缺陷 2：全局分页 `:total` 类型警告（几乎覆盖所有列表页）
- **现象**：所有带分页的页面 console 提示 `Invalid prop: type check failed for prop "total". Expected Number, got String`，同时 `[ElPagination]` 废弃用法告警。
- **根因**：[JacksonConfig.java](file:///D:/traeitem/labWork/LIS-clinical-lab-solution/lis-system/lis-common/src/main/java/com/lis/common/config/JacksonConfig.java#L39-L46) 中 `builder.serializerByType(Long.TYPE, new LongToStringSerializer())` 把**基本类型 `long`** 也注册为转字符串，于是 `PageResult.total/current/size`、各类统计计数字段都序列化成字符串，前端分页、数值解析都收到 String。
- **修复**：移除 `Long.TYPE` 的注册，仅保留引用类型 `Long`（雪花 ID 精度不丢）。经核查，全系统实体主键均为引用类型 `Long`，无基本类型 `long` 主键，安全。
- **验证**：`/api/base/items` 的 `total` 现返回数字 `208`（Int32），分页告警全站消除。
