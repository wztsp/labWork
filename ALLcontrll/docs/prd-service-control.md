## 一、项目信息

| 项 | 内容 |
|---|---|
| 项目名称 | `lis_admin`（增量功能） |
| 技术栈 | 后端 Express + TypeScript + better-sqlite3（端口 8900）；前端 Vite + React + MUI + Tailwind（端口 8901） |
| 增量范围 | 在现有服务总览页基础上，新增「启用/暂停监控」与「启动/停止服务进程」两套能力 |
| 原始需求 | 用户要求支持「启动和暂停这些服务」。经确认拆为两功能：①启用/暂停监控（轻量，复用 enabled 字段）；②启动/停止进程（重量，新增进程管理能力） |

### 上下文与现状

- **现有服务模型**（`services` 表）：`id, name, type, host, port, health_url, enabled, sort_order, created_at, updated_at`；运行时字段 `status(online/offline/unknown), last_checked_at, response_ms`。
- **现有 API**：`GET/POST/PUT/DELETE /api/services`、`POST /api/services/check`（全量检测）、`POST /api/services/:id/check`（单检）、`GET /api/services/:id/history`。
- **`enabled` 字段已存在**：后端 `findEnabled()` 已用它过滤检测范围，但**前端无 UI 展示或切换**——这是功能一的改造起点。
- **无进程管理能力**：当前系统仅做健康检测（TCP/HTTP 探测），不涉及服务进程的启动/停止——这是功能二的增量起点。

## 二、产品目标

两个功能共同解决一个核心痛点：**管理员只能"看"服务状态，不能"管"服务生命周期**。

1. **监控可开关**：管理员可一键将某服务从健康检测范围中暂停或恢复，避免已知故障/维护中的服务持续告警干扰判断。
2. **进程可管控**：管理员可在 admin 后台直接拉起或停止微服务进程，无需登录宿主机执行 `java -jar` 或 `taskkill`，缩短故障恢复与发布重启的链路。
3. **状态可闭环**：暂停监控的服务显示"已暂停"而非"离线"；启动/停止进程后，检测结果与进程状态联动展示，管理员操作后即时看到效果。

## 四、需求池

### P0 — Must Have（必须实现）

| ID | 功能 | 需求描述 | 验收标准 |
|---|---|---|---|
| P0-1 | **启用/暂停监控开关** | 在服务总览页表格新增「监控」列，每行一个 Switch 开关组件，绑定 `enabled` 字段。开启 = 纳入健康检测范围；关闭 = 排除检测。 | ① 开关即时反映 `enabled` 当前值；② 切换时调用 `PUT /api/services/:id { enabled: true/false }`；③ 操作成功后列表即时更新；④ 暂停的服务状态列显示"已暂停"徽标（灰色），不参与全量检测。 |
| P0-2 | **暂停状态展示** | 当 `enabled=false` 时，服务状态徽标显示"已暂停"而非沿用上次的 online/offline。概览卡片新增"已暂停"计数。 | ① 暂停的服务不显示在线/离线，统一显示"已暂停"；② 概览卡片 `已暂停 N` 独立计数；③ 全量检测（`POST /check`）不包含已暂停服务。 |
| P0-3 | **启动命令配置** | 服务表新增 `start_command` 字段（TEXT，可空），用于存储启动命令（如 `java -jar D:\...\lis-gateway.jar` 或启动脚本路径）。在服务配置弹窗中可编辑。 | ① 数据库迁移新增 `start_command` 列；② 服务配置弹窗新增启动命令输入框；③ 未配置启动命令的服务，"启动"按钮置灰并提示"未配置启动命令"。 |
| P0-4 | **启动进程** | 新增 `POST /api/services/:id/start` 接口。后端使用 `child_process.spawn` 拉起进程，追踪 PID，存入数据库。 | ① 已配置启动命令时可成功 spawn 子进程；② PID 持久化到数据库（进程表）；③ 返回进程信息（pid, started_at, status=running）；④ 进程已在运行时拒绝重复启动。 |
| P0-5 | **停止进程** | 新增 `POST /api/services/:id/stop` 接口。后端使用 `process.kill(pid)` 或 `taskkill`（Windows）终止进程。 | ① 进程在运行时可成功终止；② 终止后状态更新为 stopped；③ 进程不存在/已退出时返回明确提示而非报错。 |
| P0-6 | **进程状态字段** | 服务对象新增 `process_status` 运行时字段（running/stopped/crashed/unknown）。前端列表新增「进程」列展示该状态。 | ① GET /api/services 返回 `process_status`；② 前端列表显示进程状态徽标（绿色 running / 灰色 stopped / 红色 crashed）；③ admin 重启后检测存活 PID 状态是否仍在运行。 |

### P1 — Should Have（应该实现）

| ID | 功能 | 需求描述 | 验收标准 |
|---|---|---|---|
| P1-1 | **操作确认弹窗** | 启动/停止进程操作前弹出确认对话框，显示服务名 + 操作类型 + 启动命令（如适用）。 | ① 点击启动/停止后先弹确认框；② 确认后才发请求；③ 取消则不执行。 |
| P1-2 | **进程意外退出检测** | 后端监听子进程 `exit` 事件；非主动停止的退出标记为 crashed。 | ① 进程意外退出后 `process_status` 变为 crashed；② 前端列表 crashed 行红色高亮；③ 下次全量检测时 crashed 服务如有响应则提示恢复。 |
| P1-3 | **admin 重启后状态一致性** | admin 服务启动时，读取数据库中记录的 PID，检测该进程是否仍在运行。 | ① admin 重启后对已有 PID 执行存活检测（Windows 用 `tasklist /FI "PID eq xxx"`）；② 存活则维持 running，不存活则标记为 stopped。 |
| P1-4 | **进程操作状态实时反馈** | 启动/停止操作返回结果后，前端即时更新该行进程状态，无需手动刷新。 | ① 操作成功后该行进程状态列即时变更；② 操作中按钮显示 loading 态。 |
| P1-5 | **监控暂停与进程联动** | 暂停监控的服务仍可查看进程状态（进程状态独立于监控状态）。 | ① 暂停监控不影响进程检测；② 概览卡片区分"已暂停"与"已停止"的计数。 |

### P2 — Nice to Have（可选延后）

| ID | 功能 | 需求描述 | 验收标准 |
|---|---|---|---|
| P2-1 | **批量启用/暂停** | 表格支持多选 + 批量暂停/恢复监控。 | ① 可勾选多行；② 批量操作一次性更新。 |
| P2-2 | **批量启动/停止** | 表格支持多选 + 批量启动/停止进程（需确认弹窗）。 | ① 批量操作逐个执行并汇总结果；② 失败项单独标注。 |
| P2-3 | **操作日志审计** | 新建操作日志表，记录 who/when/what（启动/停止/暂停/恢复）/service/result。新增操作日志查看页。 | ① 每次进程操作落库；② 日志可按时间/服务/操作类型筛选。 |

| P2-5 | **自动重启** | 进程 crashed 后可选自动重启（带最大重试次数 + 间隔）。 | ① 可配置是否自动重启；② 达到最大重试次数后停止并告警。 |

## 五、UI 设计稿描述

### 5.1 服务总览页（OverviewPage）改造

**现有表格列**：服务名 | 类型 | 地址 | 状态 | 最后检测 | 耗时 | 操作

**改造后表格列**：服务名 | 类型 | 地址 | 监控 | 进程 | 状态 | 最后检测 | 耗时 | 操作

新增两列：

- **「监控」列**：MUI `Switch` 开关组件，绑定 `enabled` 字段。
  - 开关开启（蓝色）= 已启用监控
  - 开关关闭（灰色）= 已暂停监控
  - 切换时直接调用 `PUT /api/services/:id { enabled }`，开关旁显示 loading spinner 直到请求完成

- **「进程」列**：进程状态徽标（类似现有 StatusBadge 组件风格）
  - 🟢 running（绿色）— 进程运行中
  - ⚫ stopped（灰色）— 进程已停止
  - 🔴 crashed（红色）— 进程意外退出，行背景高亮 `#fdecea`
  - — unknown（灰色虚线）— 未配置启动命令

**操作列新增按钮**（在现有详情/历史按钮旁）：

- ▶ 启动按钮（绿色 PlayArrow 图标）— 仅 `process_status != running` 且已配置 `start_command` 时可点击
- ⏹ 停止按钮（红色 Stop 图标）— 仅 `process_status == running` 时可点击

### 5.2 服务配置弹窗（ServiceConfigDialog）改造

在现有配置项（名称、类型、主机、端口、健康URL）基础上新增：

- **启动命令** 输入框（TextField，multiline，full width）

  - 下方辅助文字：用于进程启动/停止功能；留空则该服务仅支持监控，不支持进程管控

### 5.3 操作确认弹窗（新增组件）


停止操作同理，措辞为"确认停止服务"。

### 5.4 状态语义对照

| 监控状态 (enabled) | 进程状态 (process_status) | 综合含义 |
|---|---|---|
| true + online | running | 服务正常运行中 |
| true + offline | running | 进程在但端口不通 — 可能启动中或端口配置错 |
| true + offline | stopped | 进程未启动 — 需启动 |
| true + offline | crashed | 进程崩溃 — 需排查 |
| false (暂停) | — | 已暂停监控，不检测，进程状态独立展示 |
| false (暂停) + running | running | 暂停了监控但进程仍在跑 |

## 六、待确认问题

| # | 问题 | 影响范围 | 倾向建议 |
|---|---|---|---|
| Q1 | **进程启动命令如何配置？** 各服务的启动命令格式是什么？是 `java -jar xxx.jar` 还是 PowerShell 启动脚本？前端微服务（lis-frontend）是否也需要进程管控（`npm run dev` / `vite`）？ | P0-3, P0-4 | 建议支持自由文本命令行（`child_process.spawn` 按空格拆分），前端服务如需管控同样配置命令；建议主理人提供 15 个服务各自的启动命令清单 |
| Q2 | **进程工作目录如何设定？** Spring Boot 服务通常需要在特定目录（如 jar 包所在目录）启动，是否需要额外配置 `cwd` 字段？ | P0-4 | 建议在 `start_command` 旁可选配置 `work_dir`，默认取 jar/脚本所在目录 |
| Q3 | **是否需要 Docker 容器化支持？** 当前方案是直接 spawn 进程。如果服务以 Docker 容器方式部署，启动/停止命令将变为 `docker start/stop <container>`。是否需要兼容？ | P0-4, P0-5 | 建议本期仅支持原生进程（spawn）；Docker 兼容作为 P2 — 通过命令文本间接支持（用户自行填 `docker start xxx`） |
| Q4 | **安全边界与权限**：当前 admin 后台是否有登录鉴权？进程启动/停止是高危操作，是否需要在实现进程管控前先做登录鉴权（P2-4 in prd.md）？还是信任内网环境直接上线？ | P0-4, P0-5 | 建议信任内网环境直接上线；鉴权作为前置依赖在后续迭代补齐；但操作确认弹窗（P1-1）必须实现 |
| Q5 | **admin 重启后进程状态一致性策略**：admin 服务自身重启后，数据库中记录的 PID 可能已被操作系统回收或复用。检测 PID 存活时，Windows `tasklist` 的 PID 命中是否可靠？是否需要额外校验（如进程名匹配）？ | P1-3 | 建议先做 PID 存活检测（`tasklist /FI`），P2 阶段增强为 PID + 进程名双校验 |
| Q6 | **前端服务的进程管控范围**：lis-frontend 是 Vite dev server（端口 3000）。是否需要对其支持启动/停止？还是仅对 14 个后端 Java 服务支持进程管控？ | P0-3 | 建议前端服务同样支持，但启动命令由用户自行配置（如 `npm run dev`） |
| Q7 | **停止方式选择**：停止进程用 `SIGTERM`（优雅停止）还是直接 `taskkill /F`（强制终止）？Spring Boot 服务是否需要先优雅停止（等待请求处理完）？ | P0-5 | 建议默认 `taskkill`（Windows 无 SIGTERM 等价物），后续可支持配置"优雅停止超时"——先发 HTTP 停止端点请求（如 Spring Boot actuator shutdown），超时后强制 kill |
| Q8 | **进程输出存储策略**：子进程的 stdout/stderr 是否需要持久化？存内存（admin 重启丢失）还是落库？落库的话数据量如何控制？ | P2-4 | 建议内存环形缓冲区（最近 500 行），不落库；crashed 时可导出当前缓冲用于排查 |
